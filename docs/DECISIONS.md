## Phase 12 — 세션별 기록 (2026-09-11, v1.6.0 ~ v1.13.0)

> **① 번 묶음에서 나온 것 (2026-09-11, v1.6.0)** — 착수 전 메모에 적어 둔 세 가지의 결론:
> - **경로 상수는 옮기지 않았다.** 순환 import 는 상수를 옮겨서가 아니라 **핸들러 설정을
>   진입점에만 두어** 피했다(모듈은 `logging.getLogger(__name__)` 만 쓴다). `applog.py` 는
>   표준 라이브러리 외에 아무것도 import 하지 않고, 로그 디렉터리는 `main.py` 가 인자로 넘긴다.
>   → `api_client.APP_DIR` 그대로, `tests/test_parsing.py` 의 `CACHE_DIR` 재대입 방식도 그대로.
>   **옮기는 쪽을 골랐다면 테스트까지 같이 고쳐야 했다** — 안 옮겨도 되는 문제였다.
> - **WebView2 감지는 레지스트리 읽기를 주입 가능하게** 떼어 `pv` 판정만 잰다. 이 PC 실측 `152.0.4191.66`.
> - **테스트가 실제 구멍을 잡았다**: 빈 문자열 판정이 레지스트리 리더 안에만 있어 **주입한 리더는
>   그 규칙을 비껴갔다.** 판정을 `webview2_version` 한 곳으로 옮겼다 — 로직과 배선을 따로 재라는
>   규칙이 그대로 재현된 사례다.
> - 남은 한계: **top-level import 가 실패하는 크래시는 로그에 못 남는다**(로그 설정 전에 일어난다).
>   `main.py` 가 `api_client`·`webview` 를 상단에서 import 하는 한 그렇다. 실제로 겪으면 그때 옮긴다.

> **② 번 묶음에서 나온 것 (2026-09-11)**:
> - **CI 는 `windows-latest` 로 뒀다.** 이 앱은 Windows exe 이고 `startup.py` 는 `winreg` 를
>   만진다 — 리눅스에서 도는 초록은 실제 배포 환경을 대변하지 못한다.
> - **`startup.py` 스모크는 CI 에 넣지 않았다.** GitHub 러너에는 WebView2 가 없어 `[FAIL]` 로
>   끝나는데, 그건 **앱의 실패가 아니라 러너의 사실**이다. 감지 로직은 리더를 주입하는 테스트가 덮는다.
> - **`build.bat`(exe 빌드)도 CI 에 넣지 않았다.** 지금은 매 작업마다 로컬에서 빌드해 확인하고 있다.
>   빌드가 실제로 깨지기 시작하면 그때 넣는다(전역 규칙 9번의 판정 가능한 조건).
> - **CI 가 첫 실행에서 값을 했다.** 러너 콘솔이 `cp1252` 라 스모크의 한글 `print` 가
>   `UnicodeEncodeError` 로 죽었다 — **이 PC(UTF-8 로캘)와 한국어 PC(cp949)에서는 재현되지
>   않는 버그다.** 전역 규칙이 경고한 "개발 PC 가 대표 사례가 아니다"가 그대로 나왔다.
>   `PYTHONIOENCODING=cp1252` 로 로컬 재현 → 고침 → 회귀 테스트 2건으로 못 박았다(46 → 48).
> - 사후 정리하다 **계획서가 실제와 어긋난 곳 셋**을 같이 고쳤다 — 5절 파일 구조(신규 모듈 누락),

>   `document.addEventListener` 가 없으면 앱에서는 아무 키도 안 먹는데, 그걸 가르는 건 그 한 줄뿐이다.

>   가시 구간은 `[visStart, visEnd]` 하나라 중간의 낮을 표현하지 못한다. 저녁에 실행하면

>   *교훈이 쌓였다*: 실제 시각·실제 데이터로 재는 단언은 **그 자리를 덮는지가 우연**이다.

>   변이 실험이 세 번 다 잡아냈다 — 변이를 안 돌렸으면 셋 다 통과로 남았다.

>   경계를 "대충 나눗셈"으로 두면 **큰 입력에서만** 조용히 넘친다.

## P12-22 밀린 릴리스 정리 (2026-09-12)

실측대로였다 — 최신 릴리스 `v1.2.0`, 코드 `v1.13.0`. 태그도 `v1.2.0` 까지만 있었다.

- **태그는 "버전을 올린 커밋"에 붙였다.** 기존 `v1.0.0~v1.2.0` 이 이미 그 방식이었다
  (`git cat-file -t` 로 annotated 인 것도 확인). 버전 블록의 **마지막** 커밋에 붙이는 방식과
  갈렸는데, 그렇게 하면 `v1.5.2` 태그가 그 뒤에 붙은 Phase 12 계획 커밋까지 품는다.
  **커밋 제목이 아니라 각 커밋의 `__version__` 실제 값을 뽑아 매핑**했다 — 제목만 보면
  버전을 안 올린 후속 커밋(문서·테스트)이 어느 버전에 속하는지 알 수 없다.
- **태그 날짜를 커밋 날짜로 맞췄다**(`GIT_COMMITTER_DATE`). 안 그러면 14개가 전부 오늘로
  찍혀 GitHub 릴리스/태그 목록의 시간축이 무의미해진다.
- **릴리스는 `v1.13.0` 하나만 냈다.** 과거 버전 exe 를 지금 다시 빌드해 붙이는 것은
  **그 시점의 재현이 아니다** — 그때와 의존성 버전이 다르다. 태그로 소스 이력은 남고,
  내려받는 것은 최신 하나면 된다.

### 빌드에서 걸린 것 두 가지 (실측)

- **Git Bash 에서 `cmd /c build.bat` 이 빌드를 돌리지 않는다.** 종료 코드 0 에 로그에는
  cmd 배너만 남고 exe 는 그대로였다 — **성공으로 보이는 실패**다. PowerShell 에서
  `& "$PWD\build.bat"` 로 부르면 정상이다. 종료 코드가 아니라 **산출물 타임스탬프**로 판정해야 한다.
- **PyInstaller 는 `build/` 캐시가 있으면 `checking Analysis` 만 하고 재빌드하지 않는다.**
  릴리스에 올릴 물건은 `build/`·`dist/` 를 지우고 다시 만든다. 실제로 지우고 빌드하니
  14,589,679 → **14,591,657 바이트**로 달라졌다 — 기존 exe 는 `v1.13.0` 커밋보다 26초 먼저
  만들어진 것이었고, 크기 차이가 그 사실을 뒷받침한다. **그걸 그대로 올렸으면 릴리스 자산이
  태그와 다른 소스에서 나온 물건이 될 뻔했다.**

## P12-12 업데이트 확인 (2026-09-12, v1.14.0)

GitHub 최신 릴리스를 시작할 때 한 번 확인하고, 지금 버전보다 높으면 좌하단에 배지를 띄운다.
비교까지 파이썬이 끝내고 JS 는 표시만 한다 — 무거운 네트워크를 JS 에서 하지 않는다는 규칙 그대로다.

- **`update_available` 을 캐시에 저장하지 않는다.** 이 기능의 조용한 실패는 여기 하나다:
  bool 을 굳혀 두면 사용자가 새 버전으로 바꾼 뒤에도 TTL(하루) 동안 **계속 "새 버전이 있다"**
  고 말한다. 예외도 안 나고 화면만 틀린다. 캐시에는 `latest`·`url`·`name` 만 넣고 비교는
  **매번 지금의 버전**으로 다시 한다. 테스트 이름을 `test_cached_result_is_recompared_against_current_version`
  으로 길게 둔 이유다.
- **버전 비교는 숫자 튜플로.** 문자열이면 `"1.9.0" > "1.13.0"` 이 참이 된다 — 이 앱이 실제로
  지나온 구간이라 가상의 위험이 아니다.
- **읽을 수 없는 태그는 "업데이트 없음".** `nightly` 같은 태그로 **없는 새 버전을 알리는 쪽**이
  놓치는 쪽보다 나쁘다. 모를 때 조용한 편을 고른다.
- **확인 실패를 화면에 띄우지 않는다.** 업데이트 확인은 앱의 기능이 아니라 부가물이다.
  실패하면 배지가 안 뜰 뿐이고, 오프라인이면 오래된 캐시로라도 알던 최신 버전을 쓴다.
- **스모크는 소스 도달 여부만 잰다.** 현재 버전은 앱(`main.py`)이 넘기는 값이라 `api_client` 가
  읽지 않는다 — `main` 을 import 하면 스모크가 webview(GUI)에 딸려간다. 그래서 스모크는
  `check_update("0.0.0")` 으로 부르고 최신 태그만 찍는다.

### 하네스가 부트 경로를 탈 수 있게 됐다 (이번에 실제로 구멍이 났다)

처음 쓴 배선 테스트는 `ctx.initUpdateCheck()` 를 **직접** 불렀다. 판정은 전부 보이는데
**boot.js 의 호출 한 줄을 지워도 통과**했다 — 변이 실험이 그걸 잡았다(10건 중 2건 놓침).
이 저장소에서 같은 모양의 구멍이 이번이 네 번째다(`keydown` P12-14 · `loadArchive` P12-6 ·
궤적 슬라이더 P12-16).

고친 방법은 테스트가 아니라 **하네스**였다. `maplibregl` 스텁이 없어 `initMap` 이
`new maplibregl.Map` 에서 던졌고, 그래서 `pywebviewready` 를 재현할 수 없었다. `Map`·
`NavigationControl`·`Marker` 스텁을 `harness.js` 에 넣어 `win.fire("pywebviewready")` 로
**실제 부트를 그대로 재게** 했다. 이제 배선 테스트는 "부트 전에는 핸들러가 없다 → 부트 후에는
있다" 를 잰다. 다음 기능의 배선 구멍도 같은 방법으로 막힌다.

### 같은 함정을 두 번째로 밟았다 (BOM)

화면 확인을 하려고 `%APPDATA%` 캐시에 더 높은 버전을 심었는데 **배지가 안 떴다.** 원인은
PowerShell 5.1 의 `-Encoding utf8` 이 **BOM 을 붙인 것**이다 — `json.load` 가 실패하고,
`_cache_read` 는 그걸 "캐시 없음"(첫 실행)으로 보므로 앱이 실제 API 를 다시 불러 덮어썼다.
**예외도 로그도 없다.**

이 함정은 `PLAN.md` P9-1 에 이미 적혀 있었다("`Out-File -Encoding utf8` 은 BOM 이 붙어 설정이
통째로 무시됨"). 적어 둔 것을 다시 밟았다는 뜻이라, 도구를 바꿨다 — **`%APPDATA%` 의 JSON 을
손으로 심을 때는 PowerShell 이 아니라 `.venv\Scripts\python.exe` 로 쓴다**(`io.open(..., encoding="utf-8")`).

> 참고: 앱이 쓰는 캐시는 언제나 BOM 없이 쓰므로 **실제 사용자에게는 일어나지 않는다.**
> 이것은 재현 절차의 실수였다. 다만 `_cache_read` 를 `utf-8-sig` 로 읽게 하면 손으로
> 건드린 파일에도 견디는데, 이번 범위(P12-12) 밖이라 하지 않았다.

## P12-15 발사 밀도 히트맵 (2026-09-12, v1.15.0)

### 왜 히트맵인가 — 마커가 못 하는 말이 있다

마커·클러스터는 **"어디서 몇 번"을 구조적으로 못 보여준다.** 같은 발사장에 완전히
겹친 점은 1건이나 300건이나 똑같이 보이고, 클러스터는 줌에 따라 뭉치는 기준이 바뀌어
같은 화면을 두 번 보면 다른 수가 나온다. 아카이브(P7-5)를 불러올수록 의미가 커지는
유일한 표현이라 Phase 12 의 남은 후보 중 이것을 먼저 했다.

### 테스트가 전부 초록인데 화면은 틀려 있었다 — 캡처 세 번

이번의 배울 점은 이것 하나다. **세 번의 캡처에서 두 번 틀렸고, 두 번 다 테스트는 만점이었다.**

| 캡처 | 화면 | 원인 |
|---|---|---|
| ① | 1건짜리 발사장과 21건짜리가 **똑같이 빨강** | `heatmap-weight: 1` 고정 — 점 하나로 이미 색이 포화한다 |
| ② | 최다 21건짜리가 **파랑**(램프의 40% 에서 멈춤) | MapLibre 커널은 점마다 `weight × GAUSS_COEF(≈0.399)` 를 얹는다. `1/max` 로는 부족 |
| ③ | 최다 노랑-주황, 중간 청록, 1건은 희미 | — |

①은 **기능이 제 목적을 잃은 상태**였다. "어디서 몇 번"을 보여주라는 항목인데 전부 같은
색이니 마커와 다를 게 없었다. 그런데 히트맵은 멀쩡히 그려지고, 소스에는 정확한 점이
정확한 수만큼 들어가 있어 **자동 검증으로는 잡을 길이 없다.**

→ 그래서 `heatScale()` 이 **지금 보고 있는 집합**의 최다 건수에 맞춰 가중치를 매번 다시
잡는다(필터·아카이브로 최다가 바뀐다). 이러면 눈금을 `1건 ~ 최다 N건` 으로 **숫자로**
적을 수 있다 — "적음/많음"은 아무 말도 안 한 것과 같다.

②는 **외부 라이브러리의 내부 상수를 몰라서** 생겼다. 히트맵 커널의 peak 는 weight 가
아니라 `weight × 1/√(2π)` 다(`heatmap.vertex.glsl` 의 `GAUSS_COEF`). 이걸 모르면
"가중치를 정확히 1/max 로 줬는데 왜 색이 안 차지?" 에서 막힌다. 코드에 상수로 두고
근거를 주석에 적었다.

부수적으로 `heatmap-intensity` 를 **줌에 따라 바꾸지 않기로** 했다. 강도가 줌마다
달라지면 같은 색이 줌마다 다른 건수를 뜻하게 되어 **범례의 눈금이 거짓말이 된다.**

### 소스를 따로 판 이유

기존 `launches` 소스는 `cluster: true` 다. 그 위에 히트맵을 얹으면 **클러스터 하나가
점 하나로** 세어져 밀도가 통째로 왜곡된다 — 그리고 `clusterMaxZoom` 위아래로 기준이
달라지니 **줌에 따라 밀도가 바뀌는** 히트맵이 된다. 오류는 안 난다.

대신 필터 결과는 `applyFilters()` **한 곳에서** 두 소스로 나눈다. 갈라지면 한 지도의
두 표현이 서로 다른 말을 하는데, 그건 화면으로 알아채기 가장 어려운 종류다.

### 클러스터를 숨기지 않고 흐린 이유

히트맵을 켜면 클러스터 원이 히트맵을 덮는다. 처음엔 숨기려 했으나, 클러스터 소스는

## P12-4 발사 궤적 근사선 (2026-09-12, v1.16.0)

### 보류된 Phase 4 의 대체 — 무엇을 포기하고 무엇을 남겼나

실시간 텔레메트리(4-3절)는 **무료 데이터 소스가 없어** 보류돼 있다. 실제 비행 경로는
포기하고, **발사장 좌표 + 목표 궤도 경사각**이라는 이미 가진 데이터로 상승 경로를 근사한다.

방위각은 구면 삼각법으로 푼다 — `sin A = cos i / cos φ`. 두 해 중 어느 쪽을 고르느냐가
이 계산의 전부다:

- 순행(`i < 90`) → 북동쪽 해
- **역행(`i ≥ 90`) → `180 − A`(남쪽 해)**. 반덴버그의 태양동기 발사가 남서로 나가는 이유다
- `i < |φ|` 는 물리적으로 **불가능**(그 위도에서 가능한 최소 경사 = 위도) → 정동으로 클램프.
  예외를 던지면 선만 조용히 사라진다

실제 값과 대조: 케네디→ISS 궤도 **45°**(실제 44~45°), 바이코누르→ISS **63°**(실제 61~65°),
반덴버그→태양동기 **190°**. 외부 정답표가 없는 계산이라 이 대조가 검증의 한 축이다.

### 데이터가 설계를 바꿨다 — LEO 57% 는 경사각을 모른다

착수 전에 캐시 **441건 전수**를 셌다(P11-6 에서 배운 "먼저 측정한다").

| 궤도 이름 | 건수 | 경사각 |
|---|---|---|
| Low Earth Orbit | 250 (57%) | **모른다** (28~97° 어디든) |
| Sun-Synchronous | 69 | ≈98° |
| Geostationary Transfer | 36 | ≈발사장 위도 |
| Polar | 26 | 90° |
| Suborbital | 19 | 궤도 진입 없음 |
| Unknown | 18 | 모른다 |

`orbit` 이 비어 있는 건은 **0건**인데, 정작 **가장 많은 것이 방위각을 못 정한다.**
세 가지를 놓고 골랐다:

1. **최소 에너지(=발사장 위도)로 가정하고 그 사실을 화면에 적는다** ← 채택
2. 아는 것만 그린다 → 절반 이상의 발사에서 기능이 사라진다
3. 미션명으로 보정한다(Starlink→53°, ISS/Crew→51.6°) → 맞는 것은 정확해지지만
   **표가 조용히 낡는다**. 이름 규칙이 바뀌어도 아무 신호가 없다

### "근사입니다"는 명시가 아니다

이 항목의 유일한 전제 조건이 *"실측이 아니라 근사임을 화면에 명시"* 였다. 주의 문구
한 줄로는 **무엇을 가정했는지** 알 수 없어서, 가정을 **숫자로** 적는다:

```
가정: 경사 98.0° (태양동기) · 방위 203° 남서쪽
실제 저궤도 경사는 28~97° 어디든 됩니다 — 이 선은 목표 궤도를 모를 때의 최소 에너지 가정입니다.
```

선도 **점선**으로 그린다. 실선은 실측처럼 보인다 — 문구와 같은 말을 선 모양으로도 한다.

**그리고 위치가 문제였다.** 처음엔 패널 맨 아래에 붙였는데, 캡처해 보니 긴 패널에서
**스크롤 끝까지 내려야** 보였다. 그건 명시했다고 할 수 없다 — P12-16 의 "배지가 화면 밖"과
정확히 같은 자리다. 발사 시각보다 위로 올렸고, **그 순서 자체를 테스트가 잰다.**

### 하네스가 실제 DOM 과 달라 잘못 통과했다

`탄도 비행은 선도 문구도 없다` 가 처음에 실패했는데, 원인은 앱이 아니라 **스텁**이었다.
실제 DOM 은 `innerHTML` 을 덮어쓰면 자식이 날아가는데 스텁은 `children` 배열을 그대로
들고 있어, **앞서 열었던 패널의 문구가 남아** "안 그렸는데 그려졌다"가 됐다.

이 방향의 오류는 **거짓 통과**를 만든다 — 이번엔 우연히 실패로 드러났지만, 순서가
반대였으면 조용히 지나갔다. 스텁이 실제와 다르게 동작하는 곳은 발견 즉시 고친다.

### 검증

- `tests/test_frontend.js` 394항목. 정답표가 없으니 **물리 불변식**으로 잰다:
  경사=위도면 정동 · 경사가 커지면 북쪽으로 **단조** 이동 · 역행은 남쪽으로 내려감 ·
  끝점까지 2,200km(haversine) · 모든 경도가 −180~180 · 날짜변경선 분할.
  변이 9종 전부 검출(역행 해 선택 제거·클램프 제거·경도 정규화 제거·탄도 비행 허용·
  표 조회 방어 제거·LEO 경고 제거·패널 닫을 때 미삭제·문구 미표시·날짜변경선 미분할).
- **캡처 2건(SSO·LEO).** 패널을 여는 데는 클릭이 필요한데 마우스 자동화는 이 프로젝트
  금칙이라, `index.html` 에 **임시 스크립트를 넣어 열고 되돌렸다** — P11-7 에서 타일 URL 을

## P12-19 `api_client.py` 분리 (2026-09-12, 버전 변화 없음)

### JS 분리와 사정이 달랐다 — 테스트가 전역 재대입으로 격리한다

`sats.js`(P12-23)는 줄을 옮기기만 하면 됐다. `api_client.py` 는 아니었다:

```python
# tests/test_cache.py — 격리 수단이 곧 전역 재대입이다
api_client.CACHE_DIR = os.path.join(self.tmp, "cache")
api_client._http_get = fake
```

이 넷(`APP_DIR`·`CACHE_DIR`·`SETTINGS_PATH`·`_http_get`)을 다른 모듈로 옮기면
**전역 규칙 8번**(재할당되는 전역은 이름 import 금지)에 정면으로 걸린다. 더 나쁜 건
**패치가 안 먹는데 테스트가 통과할 수 있다**는 것이다 — 임시 디렉터리 대신 진짜
`%APPDATA%` 캐시에 쓰면서.

그래서 경계를 **"전역 재대입이 없는 곳"** 에 그었다. 착수 전에 그것부터 쟀다:

- `grep "global "` → **0건**
- AST 로 옮길 함수 12개가 참조하는 모듈 전역을 전부 나열 → `MAX_VID_URLS`·`MAX_UPDATES`·
  `log`·`HTTP_ERROR_MESSAGES`·`TIMEOUT_MESSAGE` 뿐이고 **전부 같이 옮기면 되는 상수**
- 테스트가 패치하는 이름과 겹치는 것 → **없음**(옮길 함수들은 호출만 된다)

결과: 722 → **480**(상수·HTTP·캐시·설정·`get_*`·`check_update`·스모크) +
**`api_parsing.py` 225** + **`api_errors.py` 50**.

### 전면 분리(패키지화)를 기각한 이유

`http`·`cache`·`launches`·`sats`·`update` 로 전부 나누는 안도 검토했다. 가장 깨끗하지만
`test_cache.py` 46개의 패치 대상을 전부 옮겨야 하고, **잘못 옮기면 위의 조용한 실패**가 된다.
남는 480줄은 "외부에서 가져와 캐시한다"는 **한 관심사**라 더 쪼갤 이유도 약하다.

### 호출은 모듈 경유로

옮긴 함수들은 재대입되지 않으니 `from api_parsing import _parse_launches` 도 동작한다.
그래도 `api_parsing._parse_launches(...)` 로 쓴다 — **같은 파일의 이웃한 값들이
재대입되는 짝**이라, 여기만 이름 import 를 쓰면 다음 사람이 규칙의 경계를 다시 판단해야 한다.

### 모듈 이름에 `api_` 를 붙였다

`parsing.py`·`errors.py` 는 최상위 이름이라 exe 번들 안에서 서드파티 최상위 모듈과
겹칠 수 있고, **그 실패는 조용하다**(엉뚱한 모듈이 import 된다). `api_client.py` 와 짝이 맞기도 한다.

### 검증

- `test_parsing` 63 · `test_cache` 46 전부 통과, `python api_client.py` 스모크 5개 `[OK]`
- 변이 6종: 버전 비교를 문자열로(cache 5건 실패) · TLE 3줄 재동기화 제거(parsing 1건) ·
  403 문구를 404 문구로(cache 1건) · 타임아웃 판정 무력화(parsing 2건) ·
  `_friendly_error` 가 상태코드 표를 안 봄(parsing 3건) — **전부 검출**
- 앱 실행 확인(로그 무오류·캡처)

### 이번에 한 실수 하나

변이 스크립트가 파이썬 경로를 못 찾아 중간에 죽으면서 **원본 복구가 실행되지 않아**
`api_client.py` 에 변이가 한 줄 남았다. 곧바로 `grep` 으로 찾아 지웠지만,
**복구를 `finally` 에 두지 않은 것이 원인**이다. 이후 변이 스크립트는 `finally` 로 복구한다.
같은 실행에서 `capture_fixtures.py` 를 `--help` 인 줄 알고 돌려 **픽스처 3개가 실제로
다시 받아졌다** — `git checkout` 으로 되돌렸다. 골든은 의도할 때만 바꾼다.

## P13-1 발사 순서표 (2026-09-12, v1.17.0)

### 텔레메트리를 못 받는다고 "지금 어느 단계"까지 포기할 필요는 없었다

Phase 4(실시간 텔레메트리)는 **무료 소스가 없어** 보류돼 있다. 그런데 LL2 `timeline` 에는
그 발사의 **진행 순서가 상대시각으로** 들어 있다 — `GO for Prop Load`(T-38:00) →
`Ignition`(T-0:03) → `Liftoff`(T±0:00) → `Max-Q` → `MECO` → `단분리` → `착륙`.
실측 중계는 아니지만 **"지금이 어느 단계인가"는 시각만으로 말할 수 있다.**

우리는 이 필드를 **이미 받아오고 있었고 버리고 있었다**(정규화에서 안 읽었다).
Phase 13 후보를 "받아오는데 안 쓰는 데이터"로 뽑은 이유가 이것이다.

### 착수 때 쓴 커버리지 수치가 반쪽이었다

후보를 뽑을 때 **예정 발사 50건**만 보고 "10%"라고 적었다. 구현 뒤 캐시 100건
(예정 50 · **지난 50**)으로 다시 세니 **35건(35%)**이고, 거의 전부 **지난 발사**다.

그래서 이 기능의 값어치도 반쯤 달라진다: "임박한 발사를 실시간으로 따라가는 것"만이 아니라
**"지난 발사가 어떻게 진행됐는지 읽는 것"**이 오히려 더 자주 쓰인다.
**표본을 한쪽만 보고 비율을 말하면 기능의 쓰임새까지 잘못 짚는다.**

### 같은 실수를 P13-4 에서도 했다 — 그쪽은 기각으로 끝났다

P13-4 는 "`probability`·`weather_concerns` 행이 죽어 있다(56건 전부 비어 있다)"였는데,
그 56건이 **예정 50 + 픽스처 6**이었다. 지난 발사를 넣어 다시 세니 `probability` 14건 ·
`weather_concerns` 9건이고 **전부 지난 발사**다. **죽은 UI 가 아니라 발사 뒤에 채워지는 필드**다.

이걸 알아챈 것도 코드가 아니라 **캡처**였다 — P13-1 을 확인하려고 띄운 화면에
`발사 확률 70%` 가 떠 있었다. 계획서에서 기각하고 근거를 남겼다.

### 정직함을 지킨 자리 넷

1. **절대 시각은 `net_precision` 이 분 단위 이상일 때만.** 날짜만 확정된 발사에
   `05:12:58 MECO` 를 찍는 것은 없는 정밀도를 지어내는 것이다(P12-3 과 같은 자리).
2. **응답이 정렬돼 있다고 가정하지 않는다.** 어긋나면 "다음 이벤트"가 조용히 틀리고
   화면에는 그럴듯한 목록이 그대로 나온다.
3. **내용은 손보지 않는다.** 실제 응답에 `Excitement Guaranteed` 가 있고
   `Starship Landing` 이 3초 간격으로 세 번 온다. 우리가 지울 근거가 없다.
4. **읽을 수 없는 상대시각은 버린다.** 0 으로 두면 리프토프 순간에 정체불명 이벤트가 낀다 —
   시각을 지어내는 쪽이 빠뜨리는 쪽보다 나쁘다.

### 테스트가 잡은 진짜 버그: `new Date(null)` 은 epoch 0 이다

`isFinite(new Date(d.net).getTime())` 으로 막았다고 생각했는데, **`new Date(null)` 은
NaN 이 아니라 1970-01-01** 이다. 발사 시각이 미정(`net: null`)인 발사에서
**1970년 기준으로 "MECO 지남"** 이 찍힌다 — 예외도 없고 문장은 그럴듯하다.
`netMs()` 로 문자열 여부부터 본다.

## P13-2 전 세계 궤도 발사 모수 (2026-09-12, v1.18.0)

### P12-7 이 못 하던 말

P12-7 은 통계의 모수를 밝혔지만 할 수 있는 말이 **"현재 불러온 100건 기준"** 까지였다.
그 100 이 전체의 얼마인지는 **우리 데이터 안에 답이 없다.** LL2
`orbital_launch_attempt_count_year`(연내 궤도 발사 순번, 실측 98% 채워짐)가 유일한 외부 기준값이다.

이제 통계 패널이 이렇게 말한다:

> 🌍 2026년 전 세계 궤도 발사 지금까지 **215건** — 그중 **49건(23%)**을 불러왔습니다
> · 예정까지 포함하면 연말 **356건**

### 이 항목의 함정: 예정 발사의 번호는 "발사된 수"가 아니다

카운터 최대값을 통째로 쓰면 **356**이 나온다. 그런데 그 356은 **12월의 예정 발사**에 붙은
번호다 — "예정대로 가면 356번째"라는 뜻이지 이미 일어난 수가 아니다.

실측(2026-09-12):

| 구분 | 건수 | 카운터 최대 |
|---|---|---|
| 이미 일어난 발사 | 49 | **215** |
| 예정 발사 | 49 | **356** |

섞어 쓰면 **141건을 부풀린다.** 모수를 바로잡겠다고 만든 기능이 **더 큰 거짓말**을 하게 되는
자리였다. `outcome !== "upcoming"` 인 것만 "지금까지"로 세고, 예정 포함 수는 따로 적는다.

### 분자와 분모의 기준을 맞춘다

LL2 카운터는 **궤도 발사만** 센다. 우리 쪽에서 탄도 비행(`Suborbital`)까지 세면
분자와 분모가 다른 것을 세게 된다 — 비율이 조용히 부풀려진다.

그리고 **기준값이 없는 해는 아예 말하지 않는다.** 없는 말을 지어내는 것보다 침묵이 낫다.
화면에는 이 수치가 *우리가 가진 가장 최근 발사까지의 집계*임도 적었다.

### 변이 하나를 아무도 못 잡았다

"파싱에서 `orbital_year_count` 를 안 싣는다"를 걸었더니 **프론트 450항목이 전부 통과**했다.
프론트 테스트는 합성 입력으로 함수를 부르므로 **파이썬이 그 필드를 싣는지는 안 본다.**
→ `test_parsing` 에 "연내 궤도 발사 순번이 하나도 안 실렸다" 단언을 넣었다.
**순수 함수 테스트와 배선 테스트를 따로 재야 한다**는 규칙이 언어 경계에서도 똑같이 성립한다.

### 이번에 낸 실수: 같은 파일을 열면서 읽었다

```python
io.open('main.py', 'w', ...).write(io.open('main.py').read().replace(...))
```

**쓰기 모드로 여는 순간 파일이 잘린다.** 인자 안의 읽기는 그 뒤에 실행돼 빈 문자열을
돌려주고, `main.py` 가 **0줄**이 됐다. 곧바로 `test_parsing` 13건이 깨져 드러났고
`git checkout main.py` 로 복구했다 — 커밋 단위를 작게 유지한 것이 여기서 값을 했다.
**파일을 고칠 때는 읽기를 먼저 끝내고 쓴다.**

## P13-5 시간대 표기 (2026-09-12, v1.19.0)

### 이 앱은 시간이 전부인데 그 시각이 어느 시간대인지 말한 적이 없었다

카운트다운 · 발사 윈도우 · 발사 순서표 · 통과 예측 · 오늘 밤 · 타임라인 — 전부 시각이다.
그런데 `toLocaleString("ko-KR")` 이 실행 PC 의 시간대로 찍을 뿐, **화면 어디에도 그게
무엇인지 없었다.** 발사는 UTC 로 이야기되는 영역이라 "오전 05:12"는 모호하다.

**P13-1 이 이 모호함을 키웠다** — 순서표가 절대 시각을 화면에 잔뜩 늘려놨다.
기능 하나가 다른 문제를 키우는 것을 보고 다음 항목이 정해진 경우다.

### 스위치는 하나여야 한다

시각을 찍는 자리가 다섯이었다: `fmtDate` · `fmtClock` · `fmtPassTime` ·
발사 윈도우의 `hhmm` · 타임라인 날짜 라벨. **전부 `tzOpts()` 한 곳을 거치게 했다.**

갈라지면 **화면의 한쪽은 현지, 한쪽은 UTC** 가 된다 — 그건 표기가 없는 것보다 나쁘다.
예외도 없고 숫자만 다르다. 그래서 테스트가 "다섯이 모두 모드를 따르는가"를 직접 잰다.

### 표기를 어디에 붙이나

모든 시각에 ` UTC` 를 붙이면 화면이 지저분해지고, 아무 데도 안 붙이면 원래 상태다.
→ **툴바 버튼이 지금 쓰는 시간대를 상시 보여준다**(`🕓GMT+9` / `🕓UTC`).
그 버튼 자체가 표기이고, 발사 시각 행처럼 핵심 지점에만 글자로 한 번 더 적는다.

바꾸면 **이미 열려 있는 패널을 다시 그린다**(`refreshTimeViews`). 안 하면 다시 열 때까지
옛 시각이 남는데, 그게 바로 "한쪽은 현지 한쪽은 UTC" 상태다.

시간대 이름은 브라우저에서 얻고 **못 구하면 빈 문자열**이다 — 지어내지 않는다.
실제 앱에서는 `KST` 가 아니라 **`GMT+9`** 로 나온다(실측).

### 테스트가 환경에 기대면 안 되는 자리

처음에 `fmtDate` 결과를 `"2026. 05. 01. 오전 12:30"` 과 비교했더니 실패했다 —
**Node 의 ICU 는 `AM 12:30` 을, 앱(WebView2)은 `오전 12:30` 을 낸다.** 같은 코드가
환경에 따라 다른 글자를 낸다. 단언을 UTC/현지 **차이**와 구조(날짜·시각 포함 여부)로 바꿨다.

그리고 테스트 입력에서 두 번 더 헛짚었다: 날짜 경계를 못 만드는 시각을 써서
타임라인 라벨 비교가 공허하게 통과할 뻔했고, 발사 윈도우의 종료를 시작보다 앞에 둬
양쪽 다 `null` 이 나왔다. **"다르다"를 재는 단언은 입력이 실제로 달라지는지부터 확인해야 한다.**

### 화면이 알려준 것: 툴바가 밀렸다

버튼 하나가 늘자 **기본 창(1280px)에서 툴바가 두 줄로 밀렸다.** 테스트로는 절대 안 보인다.
검색창 240 → 200px, `↻ 새로고침` → `↻ 갱신` 으로 한 줄로 되돌렸다.
**다음 버튼이 들어오면 이 수법은 안 통한다** — `CLAUDE.md` "나중에" 표에 적어뒀다.

### 검증

- `test_frontend` 472항목. 변이 8종 전부 검출(포맷터 하나만 스위치를 안 보게 하기 ·
  버튼 문구 미갱신 · 설정 복원 제거 · 단축키 제거 · 저장 제거 · 기본값 뒤집기 등)
- 캡처 3회 — 현지/UTC 두 모드와 툴바 한 줄 복귀

## P13-6 관측 위치 지정 (2026-09-12, v1.20.0)

### 시작할 수 없는 안내

통과 예측(P6-2)·오늘 밤(P12-2)은 관측 위치가 있어야 도는데, 그 위치를 정하는 길이
**지도 클릭 하나**뿐이었다. 자기 집을 지도에서 찾아 눌러야 했다.

그런데 더 나쁜 것이 있었다. 오늘 밤 탭의 안내가 이랬다:

> 관측 위치가 필요합니다. 🛰 위성 패널의 **관측지 지정**을 눌러 지도를 클릭하세요.

**그 버튼은 위성을 하나 골라야 나타난다**(`#sat-ctrl` 안에 있다). 관측지를 정하려면
위성을 먼저 골라야 하고, 위성을 고르는 이유 중 하나가 통과 예측인 **순환**이었다.
기능이 아예 안 쓰였을 수 있는 자리이고, 코드로는 드러나지 않는다 — 안내 문구를 읽어야 보인다.

### 외부 지오코딩을 쓰지 않았다

"도시 이름으로 찾기"의 자연스러운 답은 Nominatim 같은 지오코딩 API다. 쓰지 않았다:

- 새 데이터 소스는 **정책·한도·에러 문구·스모크 한 줄**을 데려온다(로드맵 원칙). 난이도가 "낮음"이 아니게 된다
- **오프라인에서 못 쓴다.** 이 앱은 데이터가 캐시로 뜨는 것을 전제로 만들어져 있다

대신 ① 번들 도시 목록(한국 29곳 + 세계 주요 도시)과 ② **이미 가진 발사장 좌표**를 함께 검색한다.
발사장을 넣은 것은 데이터가 이미 있고 *"케네디 우주센터에서 보면 어떤가"* 가 이 앱에서 자연스럽기 때문이다.
**요청은 0 이다.**

### 지정 경로가 셋이 되면 한 곳으로 모은다

검색·좌표 입력·지도 클릭 — 셋 다 `setObserver()` 를 탄다. 거기에 저장·마커·통과 예측 버튼
활성화·오늘 밤 목록 갱신이 모여 있다. 갈라지면 **한 경로만 저장을 빠뜨리는** 일이 조용히 생긴다.

테스트에서 이걸 처음엔 못 쟀다. 지도 클릭 뒤 `observer.lat` 만 확인했더니, 직접 대입하는
변이가 **그대로 통과**했다. → `setObserver` 를 타야 하는 **이유**(설정 저장·버튼 활성화)를 단언에 넣었다.
**"거쳐 가는가"는 결과 값이 아니라 부수 효과로 재야 한다.**

### 손으로 적은 표는 불변식으로 잰다

도시 79곳의 좌표를 손으로 적었다 — 오타가 조용히 섞이는 종류다. 그래서:
모든 좌표가 지구 위인지 · 한국 도시가 한반도 범위(33~39°N, 124~132°E)인지 ·
남반구 도시의 위도가 음수인지 · 서반구 도시의 경도가 음수인지 · 이름이 겹치지 않는지.

그리고 `parseLatLng` 은 **첫 숫자가 위도**다. 뒤집혀도 오류가 없고 통과 예측이
**다른 하늘**을 계산한다 — 화면에는 멀쩡한 목록이 나온다.

### 하네스 지도 스텁이 실제와 달랐다

`map.on("click", fn)` 만 가정하고 **이벤트당 하나**만 담고 있었다. 실제 MapLibre 는
`on(ev, 레이어, fn)` 도 받고 **같은 이벤트에 여러 핸들러**가 붙는다(클러스터 클릭·마커 클릭·
관측지 지정이 전부 `"click"`). 스텁이 마지막 것만 남기면 배선 테스트가 **거짓으로 통과**한다.

P12-4 의 `innerHTML` 건과 같은 종류다 — **스텁이 실제와 다른 곳은 발견 즉시 고친다.**
고친 뒤 기존 테스트는 전부 그대로 통과했다(511항목).

## P13-3 발사대 재사용 간격·발사장 통산 (2026-09-12, v1.21.0) — Phase 13 종료

### 이미 있던 파서를 다시 만들지 않았다

`pad_turnaround` 는 `P63DT20M36S` 형식이다 — **P13-1 에서 발사 순서표를 읽으려고 만든
`parse_relative_time` 과 같은 ISO-8601 기간**이다. 그대로 재사용했다.
두 항목을 이틀이 아니라 한 세션에 이어서 한 덕이기도 하고, 형식을 두 번 읽지 않기로 한 결과다.

### 단위는 데이터 범위를 보고 정한다

실측(라이브 100건, 92건에 값이 있다):

| | 값 | 어디 |
|---|---|---|
| 최단 | **2.79일** | Space Launch Complex 4E (Falcon 9) |
| 최장 | **1541일** | Mu Center (Epsilon S) |

**550배 차이다.** 둘 다 "일"로 찍으면 `2.8일` 은 읽히지만 `1541.0일` 은 안 읽히고,
둘 다 "년"으로 찍으면 반대가 된다. 분 → 시간 → 일(소수) → 일(정수) → 개월 → 년으로 바꾼다.
**표기 규칙을 데이터를 보기 전에 정하면 이런 범위를 놓친다.**

### P13-2 의 함정이 그대로 다시 나왔다

`location_launch_attempt_count` 도 **예정 발사에 미리 붙어 있다.** 통산 회수로 쓰려면
`outcome !== "upcoming"` 인 것만 세야 한다 — P13-2 에서 141건을 부풀렸던 바로 그 자리다.
같은 API 의 같은 성질이므로 **카운터 필드를 볼 때마다 먼저 물을 것**이 됐다:
*이 숫자는 일어난 일인가, 예정인가?*

그리고 발사장 관점 화면에만 붙인다. 로켓·기관 관점에 "이 발사장은…"을 붙이면 거짓말이 된다.

### 이번엔 파싱 단언을 먼저 넣었다

P13-2 에서 **"파싱에서 필드를 빼는" 변이를 아무도 못 잡았다**(프론트는 합성 입력을 쓰니까).
이번에는 `test_parsing` 에 두 필드의 단언을 **구현과 함께** 넣었고, 변이 실험에서
파이썬 쪽만 정확히 실패했다. 같은 구멍을 두 번 만들지 않았다.

### Phase 13 이 끝났다

P13-4(기각)를 빼고 다섯 항목이 v1.17.0 ~ v1.21.0 으로 나갔다. 전부 **이미 받아오면서
쓰지 않던 데이터**이거나 **화면에 있는데 쓸 수 없던 것**이었다 — 새 API 도, 새 의존성도 없다.

> **다음은 후보 목록이 없다.** Phase 13 을 뽑을 때처럼 실측으로 다시 뽑아야 한다.
> 그때 확인해 둔 것: `grep TODO/FIXME` 0건 · 로그 WARNING/ERROR 0건 ·
> SATCAT 의 `PERIOD`·`INCLINATION`·`APOGEE`·`PERIGEE` 가 아직 안 쓰인다.

## 캐시 스키마 버전 (2026-09-12, v1.22.0)

### 하루에 기능 넷을 붙이고 나서야 드러난 것

Phase 13 에서 파싱에 필드를 넷 더했다 — `timeline`(P13-1) · `orbital_year_count`(P13-2) ·
`location_count`·`pad_turnaround_sec`(P13-3). 전부 화면에서 잘 동작했다.

세션 끝에 캐시 파일을 직접 열어 봤다:

```
archive_2025.json: 341건 · 새 필드 없음 → timeline, orbital_year_count,
                                          location_count, pad_turnaround_sec
launches.json:     100건 · (전부 있음)
```

**지난 연도 아카이브는 TTL 이 없어 영구 캐시다.** 2025년을 이미 불러온 사용자는
그 해 발사에서 **발사 순서표도, 발사장 통산도, 전 세계 모수도 영원히 못 본다.**
오류도 경고도 없다.

**`launches.json` 은 TTL 15분이라 저절로 나았고, 나는 개발 중 두 번이나 `force=True` 로
갱신했다** — 그래서 화면에서는 아무 문제가 없어 보였다. 캡처를 세 번 떠도 안 보이는 종류다.

### 고친 방법과, 그게 만든 새 위험

캐시를 `{"schema": N, "data": …}` 봉투에 담고, 읽을 때 버전이 다르면 **없는 것으로 본다**.
그러면 지난 연도 아카이브도 다시 받는다.

**그런데 이게 더 나쁜 것을 만들 뻔했다.** 스키마가 바뀐 직후 오프라인이 되면
정상 경로가 캐시를 버리므로 **화면이 통째로 빈다** — 전역 규칙(실패해도 화면이 비지 않게)을
정면으로 어긴다. 그래서 `_stale_fallback()` 을 뒀다: **네트워크가 실패했을 때만**
모양이 달라도 옛 캐시를 쓴다. 새 필드가 빠진 화면이 빈 화면보다 낫고, 그 상태는
`stale=True` 로 "저장된 데이터 표시" 경고가 함께 뜬다.

### 그 폴백이 도입 당일 값을 했다

실제 캐시로 확인하려고 `get_archive(2025)` 를 불렀더니 LL2 가 **429** 를 돌려줬다
(오늘 요청을 많이 썼다). 결과:

```
아카이브 2025 조회 실패: HTTP Error 429: Too Many Requests
→ 341건 · stale=True · "요청이 많아 잠시 제한됐습니다(시간당 한도)"
```

**폴백이 없었으면 그 화면은 통째로 비었다.** 캐시 파일도 덮어쓰지 않아, 한도가 풀리면
그때 다시 받는다. 설계가 옳았다는 증거를 하필 같은 날 받았다.

### 배운 것

- **기능을 여럿 이어 붙인 날에는 그 데이터가 어디에 굳어 있는지 한 번 확인한다.**
  화면·테스트·캡처가 전부 통과해도, 영구 캐시 안에서는 옛 모양이 살아 있다.
- **TTL 이 없는 캐시는 스키마 버전이 필수다.** TTL 이 있으면 시간이 고쳐 주지만
  영구 캐시는 아무도 안 고쳐 준다.
- 규칙으로 박았다(`CLAUDE.md`): *정규화 결과의 모양을 바꾸면 `CACHE_SCHEMA` 를 올린다.*

### 검증

- `test_cache` 56항목(스키마 10항목 추가). 변이 6종 전부 검출 —
  봉투 없이 저장 · 스키마 불일치 무시 · 옛 캐시 그대로 읽기 · 실패 경로 폴백 제거 ·
  아카이브 폴백 제거 · 폴백을 아무 때나 허용
- 핵심 세 항목: **지난 연도 아카이브도 모양이 다르면 다시 받는다** /
  **모양이 같으면 여전히 영구다**(요청을 늘리지 않는다) / **오프라인이면 옛 모양이라도 보여준다**

## 정기 점검 (2026-09-12) — 화면을 켜 보고서야 나온 것

Phase 13 을 끝낸 뒤 "전체 점검"을 돌렸다. **정적 점검 19항목**(테스트·버전·설정 키·죽은 코드·
HTML id·CSS·인코딩·문서 링크·비밀·저장소 크기)에서는 문서 결함 둘만 나왔다:
`PLAN.md` 의 낡은 "다음 착수" 표(Phase 13 절과 서로 다른 말을 하고 있었다)와
`CLAUDE.md` 파일 구조 표(JS 15개라고 적혀 있었는데 실제 17개).

**그런데 정작 중요한 둘은 정적 점검 밖에 있었다.**

### ① CI 가 다섯 커밋 동안 빨간불이었다

```
로컬: 530 passed, 0 failed
CI:   526 passed, 4 failed     ← v1.19.0 부터 5번 연속
```

**CI 러너는 UTC** 다. 시간대 테스트(P13-5)가 *"현지 시각과 UTC 가 다르다"* 를 재는데,
UTC 환경에서는 그 둘이 **같아져** 실패한다. P13-5 때 "로캘 문자열에 기대지 않는다"는
고쳤지만 **시간대 자체에 기댄 것**은 못 봤고, **푸시 후 CI 를 확인하지 않았다.**

→ `tests/test_frontend.js` 가 맨 위에서 `process.env.TZ = "Asia/Seoul"` 로 **고정**한다.
로컬(KST)·UTC·America/New_York 셋 다 통과하고, 고정이 안 먹으면
*"테스트 시간대가 UTC 가 아닌 곳으로 고정돼 있다"* 가 **가장 먼저** 실패한다(변이로 확인).

### ② "오늘 밤" 탭이 도입 이래 줄곧 죽어 있었다

기능을 여섯 개 한 화면에 켜고 확인하다 발견했다:

```
TypeError: favSats.includes is not a function
  at tonightTargets (satpass.js:200)
```

`favSats` 는 **Set** 이다. 같은 저장소의 다른 다섯 곳은 모두 `.has()` 를 쓰는데 여기 한 곳만
`.includes()` 였다. **관측지가 설정된 상태에서 "오늘 밤" 탭은 아무 일도 하지 않았다** —
탭이 안 바뀔 뿐 화면에는 오류가 안 보인다. `git log -S` 로 보니 **P12-2 도입(v1.7.0) 그 커밋**부터다.

**왜 테스트가 못 잡았나**: 기존 테스트는 **관측지가 없는 경로만** 덮었다. 그쪽은 막힌 안내를
내고 끝나므로 예외가 날 자리에 아예 닿지 않는다. **조건 분기는 "그 분기로 실제로 들어가는"
상태를 만들어 재야 한다.**

고친 뒤 하나 더 나왔다: 그 조건은 **애초에 아무 일도 하지 않았다.** `satrecs` 에는
`loadSatellites` 가 SGP4 레코드를 만든 것만 담으므로 `rec` 없는 항목이 없고,
`if (!isFav && !r.rec) continue;` 는 언제나 거짓이다. 죽은 조건을 걷어냈다.

### 배운 것

- **"전체 점검"이라 부르려면 CI 와 화면이 들어가야 한다.** 정적 점검 19항목은 전부 초록이었는데
  진짜 결함 둘은 그 바깥에 있었다.
- **푸시한 뒤 CI 를 본다** — `gh run list --workflow=tests.yml --limit 5` 한 줄이면 된다.
- 기능을 여럿 만든 날에는 **그것들을 한 화면에 동시에 켜 본다.** 개별 캡처는 전부 정상이었다.
