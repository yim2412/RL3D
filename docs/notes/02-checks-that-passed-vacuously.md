# 공허하게 통과한 검사들

> 좌표가 **전부 `NaN`** 인데 검사가 통과했다. 상수를 **0 으로 바꿨는데** 경계 테스트가
> 통과했다. 그리고 애초에 **한 번도 검증된 적 없는 계산**이 있었다.
> 셋 다 테스트는 초록이었다.
>
> 2026-07-26 ~ 2026-08-20 · 근거 커밋은 맨 아래

## 1. 좌표가 전부 NaN 인데 통과했다

프론트엔드 회귀 테스트를 만들었다. 브라우저·마우스 없이 Node `vm` 에 스텁 DOM 을
올리고 `web/js/*.js` 의 함수를 직접 부르는 방식이다.

위성 계산에는 실제 라이브러리(`satellite.min.js`)가 필요해서 그걸 `vm` 에 올렸다.
**앱과는 별도 컨텍스트에** 올렸다 — 라이브러리는 독립적이니 따로 두는 게 깔끔해
보였다.

결과가 이랬다.

```js
const passes = computePasses(satrec, observer, ...);
assert(passes.every(p => p.maxElevation <= 90));   // ✅ 통과
assert(passes.every(p => p.start < p.end));        // ✅ 통과
```

**통과했다. 그리고 아무것도 검증하지 않았다.**

`satellite.js` 내부에 `date instanceof Date` 검사가 있다. **별도 realm(vm 컨텍스트)의
`Date` 로 만든 객체는 그 검사에서 `false` 가 된다.** 생성자가 다른 객체이기 때문이다.
그래서 라이브러리가 입력을 유효한 날짜로 인정하지 않았고, **계산 결과가 전부 `NaN`**
이 됐다.

`NaN` 이 나오면 통과 목록이 비거나 전부 `NaN` 인 항목이 된다. 그러면:

- 빈 배열의 `every()` 는 **공허하게 참**이다
- `NaN <= 90` 은 `false` 라 항목이 있으면 잡히지만, **애초에 항목이 안 생겼다**

**브라우저에서는 없는 문제다.** realm 이 하나뿐이니까. 즉 **테스트 환경이 실행 환경과
달라서만 생긴 결함**이고, 그 결함이 하필 **검사를 무력화하는 방향**으로 나타났다.

고침은 한 줄이다 — 실제 라이브러리를 **앱과 같은 vm 컨텍스트**에 올린다.

> **`every()`·`all()`·`filter().length === 0` 은 대상이 비면 항상 통과한다.**
> 전칭 검사를 쓸 때는 **대상이 비어 있지 않다는 것을 먼저 단언**해야 한다.
> 여기서는 `passes.length` 가 하루 2~12회 범위인지를 함께 봤어야 했다 — 실제로
> 지금은 그 검사가 들어가 있다(아래 3번).

## 2. 상수를 0 으로 바꿔도 통과했다

창 복원 좌표가 화면에 최소 `120×40px` 걸치는지 검사하는 로직을 만들었다
([노트 01](01-not-broken-but-it-looked-broken.md) 참조). 경계 테스트를 이렇게 썼다.

처음엔 기대 좌표를 `MIN_VISIBLE_W` 로 **계산해서** 넣었다. 깔끔해 보인다 — 상수를
바꾸면 테스트도 따라가니 유지보수도 편할 것 같다.

**그런데 `MIN_VISIBLE_W` 를 0 으로 바꿔도 통과한다.** 기대값이 그 상수로 계산되므로
**상수가 움직이면 기대값도 같이 움직인다.** 검사하는 것이 "이 문턱이 맞나"가 아니라
"이 식이 자기 자신과 같은가"가 된다.

고침은 **좌표를 직접 적는 것**이다. 지금 테스트는 이렇게 되어 있다.

```python
# tests/test_parsing.py   PRIMARY = (0, 0, 1920, 1040) · 창 크기 1280×800
def test_barely_visible_edge_counts(self):
    """1920 폭 화면에 가로 120px 만 걸친 창 — 잡아서 옮길 수 있으니 허용."""
    self.assertTrue(main_mod._rect_visible(1800, 100, self.W, self.H, [self.PRIMARY]))

def test_one_pixel_less_than_minimum_is_rejected(self):
    """가로 119px — 임계값(120)이 실제로 쓰이는지 잰다."""
    self.assertFalse(main_mod._rect_visible(1801, 100, self.W, self.H, [self.PRIMARY]))
```

숫자가 박혀 있어 상수를 바꾸면 테스트가 깨진다. **그게 맞는 동작이다** — 문턱을
바꿨으면 그 사실이 어딘가에서 실패로 드러나야 한다.

> 이건 뮤테이션으로 잡았다. v1.5.2 에서 다섯 종을 넣고 전부 검출되는지 확인했는데
> (타임아웃 `reason` 검사 제거 · 403 문구 제거 · 캐시 미삭제 · **최소 노출폭 0** ·
> 창 방어 무력화), **네 번째가 안 잡혀서** 테스트를 다시 썼다.

## 3. 한 번도 검증된 적 없는 계산

프론트 테스트를 62항목까지 채우고 나서 무엇을 덮고 있는지 세어 봤다.

**유틸·분류·설정만 있었다.** 정작 **틀려도 화면으로는 알 수 없는 계산 로직**이 통째로
비어 있었다. 그중 통과 예측(`computePasses`)은 **한 번도 검증한 적이 없었다.**

지도 클릭으로 관측 위치를 정하면 향후 24시간의 위성 통과를 계산해 시각·방위·최대
고도를 보여준다. 외부 API 없이 SGP4 로 직접 계산한다. **틀려도 그럴듯한 숫자가 나온다** —
"오후 7시 32분, 북서 방향, 최대 47도"가 맞는지 화면만 보고는 알 수 없다.

### 정답표가 없는 계산을 어떻게 재나

골든값을 만들 수 없다. 외부 정답이 없고, 있어도 시각이 흐르면 값이 바뀐다.

**물리 불변식으로 쟀다.**

| 불변식 | 왜 참이어야 하나 |
|---|---|
| 경사 51.6° 위성은 **남극(−82°)에서 통과 0건** | 궤도 경사보다 높은 위도는 지나가지 않는다 |
| 통과 간격은 **궤도 주기의 정수배 근처** | 같은 지점 위를 지나려면 정수 바퀴가 돌아야 한다 |
| 하루 **2~12회** | LEO 의 물리적 범위 |
| `minEl` 을 올리면 통과 수가 **단조 감소** | 조건을 좁히면 결과가 늘 수 없다 |
| 최대 고도 **90° 이하** | 천정이 상한 |
| 통과 구간끼리 **겹치지 않는다** | 하나의 통과가 끝나야 다음이 시작된다 |

정답을 모르지만 **틀렸다는 것은 알 수 있는** 성질들이다. 그리고 이 검사들이 실제로
일한다는 것도 확인했다 — 뮤테이션 5종을 넣으니 전부 잡혔다.

```
날짜변경선 끊기 제거    → 2건 실패
고도 ↔ 방위 혼동        → 6건 실패
통과 병합 실패          → 2건 실패
타임라인 부등호 반전    → 1건 실패
사이드바 정렬 반전      → 1건 실패
```

**"고도↔방위 혼동"이 6건을 깬 것이 특히 중요하다** — 그게 이 계산에서 가장 그럴듯하게
틀릴 수 있는 실수이기 때문이다. 두 값 다 각도라 타입으로는 안 걸린다.

62 → **102항목**이 됐다.

## 제품 코드에도 같은 일이 있었다

테스트만 공허하게 통과하는 게 아니다. **한 번도 실행되지 않는 분기**가 제품에 있었다.

네트워크 오류를 사람 말로 바꿔 보여주는 `_friendly_error` 다. 고치기 전에는
`URLError` 검사가 타임아웃 검사보다 **위에** 있었다.

**`urlopen` 은 타임아웃을 그대로 던지지 않는다.** `URLError(reason=timeout)` 으로
감싼다. 그래서 위쪽 `URLError` 검사에 먼저 걸리고, **아래 `isinstance(e, TimeoutError)`
분기는 한 번도 실행되지 않는 죽은 코드**였다.

지금은 판별을 함수로 빼고 순서를 바꿨다. 그 함수의 docstring 이 경위를 들고 있다.

```python
# api_client.py
def _is_timeout(e):
    """타임아웃 판별.

    urlopen 은 타임아웃을 그대로 던지지 않고 URLError(reason=timeout) 으로 감싼다
    (2026-08-20 실측) — isinstance(e, TimeoutError) 가 그래서 False 다. URLError 를
    먼저 잡으면 서버가 느릴 뿐인데도 "인터넷 연결을 확인하세요" 라고 잘못 안내하게
    되므로 reason 까지 들여다본다.
    """
    if isinstance(e, TimeoutError):
        return True
    reason = getattr(e, "reason", None)
    if isinstance(reason, TimeoutError):
        return True
    return "timed out" in str(reason).lower()
```

증상은 조용하다. 예외도 안 나고 로그도 정상이다. 다만 **서버가 느릴 뿐인 상황에서
사용자는 "인터넷 연결을 확인하세요"를 봤다.** 인터넷은 멀쩡한데.

**실제 타임아웃을 유발해서** 확인한 뒤 `reason` 까지 보도록 고쳤다. 같은 점검에서
403 전용 문구도 채웠다 — 그동안 `서버 응답 오류(403).` 로만 보였는데, **403 은 이
앱이 실제로 겪는 실패다**(Celestrak 은 대형 그룹을 짧은 간격으로 거듭 받으면 막는다).
상태코드→문구를 `HTTP_ERROR_MESSAGES` 표 한 곳으로 모으고 404·500·502·503·504 도
함께 채웠다.

## 네 건의 공통점

| | 왜 아무도 몰랐나 |
|---|---|
| 별도 realm → `NaN` | 전칭 검사가 **빈 대상에 공허하게 참** |
| 상수로 계산한 기대값 | 검사가 **자기 자신과 비교** |
| 통과 예측 무검증 | **화면으로는 알 수 없는** 영역이라 |
| 죽은 예외 분기 | 위쪽 검사가 **먼저 잡아서** |

넷 다 **아무것도 실패하지 않았다.** 테스트는 초록이고 앱은 안 죽는다. 그래서 각각
다른 방법으로 찾아야 했다 — 하나는 하네스를 고치다가, 하나는 **뮤테이션**으로,
하나는 **덮은 범위를 세어 보고**, 하나는 **정기 점검에서 코드를 읽다가**.

## 이 건에서 남긴 규칙

**전칭 검사(`every`·`all`) 앞에는 대상이 비어 있지 않다는 단언을 둔다.** 빈 집합은
모든 전칭 명제를 만족한다. 그리고 계산이 조용히 `NaN` 을 내는 경로가 있으면 그 상태가
정확히 "빈 집합"으로 나타난다.

**경계 테스트의 기대값은 상수로 계산하지 않고 직접 적는다.** 상수로 계산하면 그 상수를
바꿔도 통과한다 — 검사하려던 문턱이 검사에서 빠진다.

**골든을 만들 수 없어도 검증할 수 있다.** 정답표가 없으면 **불변식**을 쓴다. 정답은
몰라도 "이건 틀렸다"는 알 수 있는 성질이 대개 있다.

**테스트가 실행 환경과 다르면 그 차이가 검사를 무력화하는 쪽으로 나타날 수 있다.**
realm·런타임 버전·인코딩 — 브라우저에선 없던 문제가 하네스에서만 생기고, 하필 조용히
통과시킨다.
